# 中文理解指南

本指南帮助学生理解和检查作品。它不代表学生已经逐行人工核验、独立复现或完成理解测试。真实实验记录以 `results/`、冻结记录和官方评分 JSON 为准。

## 这项任务到底做什么

每题已经有四段候选推理和对应的 1,024 维固定表示。程序只返回 0、1、2、3 中的一个候选下标，不生成新答案，也不在线调用语言模型。官方分数判断所选候选的最终数字答案是否与参考等价；它不检查推理每一步。即使最终答案正确，文字里也可能有错误。

同一题可能有多个正确候选。标签 `y[i,j]` 由未修改的官方 `parse_answer` 得出：候选解析成功且等于本题参考，就标 1。不能只挑一个正确候选标 1、把其他正确候选标 0。

## 模型怎样选择

基础模型将每个候选的 embedding 输入一个共享线性打分器。最终模型还加入该 embedding 与四候选均值的逐坐标绝对差，以及 16 个统计特征，总共 2,064 维。统计包括与其他候选的余弦相似度、答案出现次数、解析成功情况、长度和答案格式等。特征没有读取正确标签或题目 ID。

训练集均值和标准差用于标准化；推理时只加载已保存统计量，不能在新 batch 上重新 fit。得分是标准化特征与权重的点积加偏置。四个候选共用同一个打分函数，选择最大值；精确并列时选第一个。

我们比较逐候选 BCE 和多正例 listwise 损失。后者为：

`L = logsumexp(四个候选分数) - logsumexp(所有正确候选的分数)`。

这样提高的是“把分数集中到任意正确候选”的目标，而不是强迫四个位置只有一个正确标签。全正例题的这个损失和数据梯度为零，这是公式本身的性质。加上 L2 正则化限制权重规模。最终选择 L2=0.1 的 relation/listwise 模型。

## 关键代码怎么读

- `code/common.py`：官方加载、解析和评分，保持不变。
- `code/mp2/features.py`：验证输入、解析候选答案、构造无标签特征和多数投票。
- `code/mp2/training.py`：只允许 train/validation 的开发加载器；标签、损失和梯度；训练内部筛选；最终拟合；三折 OOF 校准。
- `code/mp2/model.py`：安全加载数值 checkpoint、固定特征打分、所选答案置信度。
- `code/solution.py`：正式接口，输出真实 Python int 的列表。
- `code/tools/evaluate.py`：分别启动官方预测、评分进程；test 必须验证冻结记录；完整计时。
- `code/tools/analyze_reliability.py`：仅 train/validation 诊断，不重新训练、不选 test 模型。

## 为什么没有数据泄漏

六个主要配置先在 train 内部按题 80/20 切分筛选，不能把同题四候选拆开。每个模型家族选一个配置，再用全部 train 拟合并查看 validation。标准化在相应训练部分拟合。最终没有把 validation 并入训练。

置信度校准单独用 train 的三折 OOF 预测：每一题的上游模型没有拟合过该题。校准事件是“当前所选最终答案是否正确”，信号是最大分数、前两名差距、所选答案的组内一致比例。校准器不改变所选下标，也不拟合 validation。

在 `submission/PRE_TEST_FREEZE.json` 固定模型、配置和哈希后，才运行一次正式完整 test；测试结果没有反向改变参数。报告只读取已经产生的聚合官方 JSON，不读取测试逐题参考或错误案例。测试表现不好也不能继续拿测试分数选择模型。

## 实际得到什么

所有下列开发比较均为完整 798 道 validation；hard 子集固定为至少两个不同可解析答案，共 355 题。

| 方法 | Validation | Hard |
|---|---:|---:|
| 固定候选 0 | 624/798 = 78.1955% | 54.9296% |
| 答案多数投票 | 688/798 = 86.2155% | 69.0141% |
| Embedding + BCE | 715/798 = 89.5990% | 77.1831% |
| Relation + BCE | 704/798 = 88.2206% | 73.5211% |
| Relation + listwise | 724/798 = 90.7268% | 79.4366% |

负结果很重要：仅加入 relation 特征并使用 BCE 反而下降；不能声称“所有改动都有用”。另一个 listwise L2=.01 内部筛选运行达到 200 次迭代上限，未收敛且未被选中，日志保留。

最终模型比 embedding BCE 高 1.1278 个百分点；开发阶段 2,000 次题级配对 bootstrap 的 95% 区间为 [-0.7519, 3.1328]，跨过零，不能说显著改善。相对多数投票高 4.5113 个百分点，但验证集选模仍会造成乐观偏差。

最终冻结官方 test 为 **348/467 = 74.51820128479658%**，见 `results/test-score.json`。test 只包含有答案分歧的题，而完整 validation 包含较容易的一致组，因此不能把 90.73% 当成测试预期。hard validation 更相关，但也不保证与 test 同分布。

## “可靠”能说到什么程度

验证集 Brier=0.06771253，ECE=0.021821。ECE 使用 10 个等宽置信度箱，报告每箱人数；空箱不计。Brier 是预测概率与 0/1 正确事件的均方误差。数值较低不等于“永不出错”，小样本分箱也有噪声。

`results/reliability/reliability.png` 左图比较置信度与实际准确率，右图按置信度保留不同数量题目后的错误率。正式评测仍必须回答全部题，不能弃掉困难题来报高分。

AI 对验证例子的解释仅供理解，未作过程监督：Megan 例子把 broken 和 cracked 的数量混淆；concert 例子最终数字正确却带有自相矛盾时间陈述；Rose 例子在计算 present 数量时遗漏 girls，估计置信度仍约 0.95。另有措辞与参考可能存在解释张力的例子，仍按官方参考评分，未擅自纠正数据。完整证据在 `results/reliability/failure_cases.md`。

## 八个自查问题及参考答案

1. **为什么随机基线不是 25%？** 每题可能有多个正确候选；其期望为每题正确候选数除以四的平均。validation 约 75.6892%。
2. **为什么不能选一个正例后把其他候选全标负？** 那会把其他同样正确的最终答案错标为负，违背评分语义。
3. **listwise 在全正例题上为什么没有数据梯度？** 两个 logsumexp 的集合相同，相减恒为零。
4. **为什么先用 train 内部筛选？** 降低重复试探官方 validation 的次数；并保留按题分组和折内拟合预处理。
5. **四路 softmax 最大值等于所选答案正确概率吗？** 不一定，因为多个候选可以同时正确；需要针对所选事件独立校准、验证。
6. **Embedding-only 是没有看推理吗？** 不是。官方 embedding 编码完整推理，移除显式长度特征也不能证明没有长度信息。
7. **最终 test 分数低于 full validation 后可以调 L2 吗？** 不能据测试反向选模；应接受冻结结果并解释数据构造和不确定性。
8. **最终答案正确意味着推理有效吗？** 不意味着；官方只检查最终数字，错误的中间陈述也可能碰巧得到正确答案。
