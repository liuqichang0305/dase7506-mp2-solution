七、阶段 4：先跑通基线，再实现改进模型

按优先级实际运行，不要求把所有可选方法都做完。最低应有可解释基线、轻量学习基线、至少一种有依据的改进尝试和关键消融。若复杂方法未提升，最终可保留简单模型，如实分析负结果。

A. 无训练基线
1. 固定候选 0，作为下限参照。
2. 多数答案投票：用官方 parse_answer 对已有候选分组，不把解析失败 None 聚成“有效答案”；并列/全部无效时用预先固定的确定性规则。
3. 可报告理论随机期望。若实际实现随机基线，固定 seed 且不依赖题目 ID，避免将一次随机幸运结果作为改进。

B. 第一版学习基线
1. 每个候选使用提供的 1024 维 embedding，训练带正则化的 logistic regression 或小型 MLP verifier；四候选共享打分器。
2. 独立逐候选 BCE 可保留全部正例；验证时逐题选最高分。比较候选 AUC 可以辅助诊断，但正式选模主指标仍是逐题 selection accuracy。
3. 标准化仅 fit train，保存所需统计量；不必要的变换不要增加复杂度。记录参数数目、文件大小、训练时间、预测总时间。

C. 改进候选（至少实测一个，默认优先 C1+C2）
C1. 候选关系特征：本候选 embedding、与组均值/其他候选的差、相似度；最终答案出现次数、是否多数、并列状态、可解析性等。不要使用正确标签形成推理特征。
C2. 与目标相符的组级训练：比较 BCE 与多正例 listwise loss。
    对同题四个分数 s_j、正例集合 P：
    L = logsumexp(s_0,s_1,s_2,s_3) - logsumexp({s_j: j in P})。
    实现数值稳定的 logsumexp，保持所有正例。全正例组对此 loss 梯度为零是目标的性质，需说明；可比较 BCE 或合理混合目标，混合权重只能在允许开发数据中选择。
C3. 可解释文本/数值特征：字符/词数、终答案标记、数字数量、简单算式一致性、题目数字与解答数字关联。所有规则由 train/validation 证据与一般数学结构形成，不按具体题目补丁。
C4. 轻量 TF-IDF/Hashing+线性模型，或有限维度的浅树模型，作为文本信息对照；词表、IDF、特征选择必须只用 train fit，检查资产大小。
C5. 有互补错误证据时考虑 2–3 个小模型的分数融合或少量种子 ensemble。所有成员都纳入 CPU 时间和 16 MiB；没有明显收益就不融合。

如果实现算式核查，只用受限解析器/AST 白名单和有限算术；限制表达式长度、深度、指数、分数规模与运行时。不能对候选文本用 eval/exec。算式正确不代表理解题意正确，不能据此宣称推理已验证。

若训练用 PyTorch 而推理可用 NumPy，可导出矩阵减少启动成本；导出后验证分数误差、argmax 一致性，不能把近似导出当成天然等价。依赖成本以真实外部计时判定。

八、阶段 5：评估、自动更新和停止条件

先用 train 内部按题划分的固定 CV/OOF 做小范围筛选，控制对官方 validation 的反复试探。预先写明有限搜索空间、最大运行次数和总时间预算。建议先最多约 12 个主要配置，不把这个建议视为课程硬限制；有明确新假设才扩大。

每个实验必须记录：experiment_id、父实验、假设、代码 commit/未提交 diff 哈希、数据版本、特征、loss、seed、超参数、训练折、训练/搜索开销、完整 validation accuracy、hard accuracy、推理时长、资产 bytes、失败日志与结论。失败结果也保留。

迭代闭环：
1. 跑初版 → 保存真实预测与官方验证分数。
2. 分析 train/validation 错误类型与模型分歧。
3. 每轮只提出少量明确改动，说明预期解决什么错误。
4. 实施 → 用相同 split/协议重评 → 跑相关回归检查。
5. 对有希望的改动做消融、多 seed 或 grouped CV 稳定性验证。
6. 验证集更好且资源合规才纳入候选；没有提升则保留失败证据并回退。
7. 依据预先规则选择最终方案，不能根据 test 决定模型、seed、阈值、融合权重或功能开关。

建议选择规则：主要参考完整 validation selection accuracy，同时检查 hard 子集、seed/CV 稳定性和资源余量；相近结果优先简单、小资产、快且稳定的方案。不要把微小差异说成显著进步。配对 bootstrap 按题重采样给出准确率差异区间，并说明反复选模会让验证集估计乐观。

必要消融至少选一个与研究假设直接相关的比较，时间允许做 2–3 个：
- embedding-only vs 加候选关系特征；
- 独立 BCE vs 多正例 listwise；
- 单模型 vs 融合；
- 显式长度/格式特征有无；
- question+final-answer 文本分支 vs full-solution 文本分支。

消融解释必须诚实：给定 embedding 编码整段推理，保留它就不能宣称“没有看到 reasoning”；真正 question+answer-only 实验必须移除这些 embedding 和所有源自 reasoning 的特征。去掉显式长度特征也不能声称 embedding 已没有长度信息。

停止条件：连续两轮主要改动没有稳定收益、预定预算到达、或进入提交缓冲期时，停止探索并锁定当前最佳合规方案。不要为了尝试所有模型错过提交。若在 10 月 29 日执行，优先安排 29–30 日完成基线/迭代，31 日完成冻结/复现/提交，并留数小时处理链接、账号和报告问题；按实际时间动态压缩可选实验。

九、阶段 6：可靠性与错误分析

必须回答“为什么值得信任”，而不只给一个榜单数字。

1. 定义可靠性事件：当前所选候选的最终数值答案是否正确。max softmax、score margin、entropy 只是可用信号，不能未经验证当作正确概率。
2. 如需训练融合器、Platt/温度/其他校准器，只使用 train 内按题产生的 OOF 预测或 train 内独立留出子集拟合。上游预处理也在各折内 fit；不要把 validation 变成校准器的训练集。
3. 在独立于校准拟合的 validation 上报告：可靠性图、Brier score、声明 bin 规则的 ECE，以及若干置信度分桶准确率和样本数。必要时使用 cross-fitting；阐明样本量与选择偏差。
4. 画 risk–coverage/accuracy–coverage 曲线说明低置信度题的风险。正式输出仍必须回答每一题，不能弃答或通过删题提高 accuracy。
5. 对比方法一致/分歧组、答案一致/分歧组、可解析/解析异常组、长度/候选正确数等开发子集。给出子集分母，避免只报最好看的局部结果。
6. 从 train/validation 选取有代表性的失败案例：多数同错、算术正确但忽略条件、答案偶然正确、格式造成解析失败等。明确人工归因是解释性分析，不是额外过程监督标签。
7. 报告准确率—时间—资产大小的权衡，解释额外计算是否值得。

4. 对比声称分数与真实复现分数，检查 split、模型版本、配置、解析器、环境和 asset 完整性。安装失败不等于 0 分，小数舍入或数值差异不自动构成造假。
5. 写事实性评审：复现成功/存在阻塞，测得数值与差异，最小复现步骤，证据链接，可能原因和未解决问题。不能凭猜测指控作弊或保证奖励。
6. 有真实 reproduced score 后，通过 MP2 网站 Peer Review Report 提交目标 submission number 与 reproduced score；保留页面生成 payload 并实际创建评审 Issue。当前 schema 为 dase7506/peer-review-v1，按实时页面为准。
7. 没跑出有效分数时只保留阻塞报告，不捏造 reproduced score 以通过表单；需要老师处理时给我可发送的说明，不擅自邮件联系。
8. 保存 peer-review Issue URL/编号和证据。若有人质疑我的提交，用冻结版本与日志复现答复；不偷偷替换原 checkpoint 或改写历史分数。任何修订都单独标注、保留原提交，以教师决定为准。

该阶段属于本工作流要求的延伸任务，不要把“必须评审多少份”或“完成就奖励”说成官方保证。至少完成一份可运行作品的真实复现评审，若外部阻塞无法完成则准确列明。
